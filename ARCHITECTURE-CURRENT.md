# EGEN Master Deck — Current Architecture (15 Sep 2026)

## Purpose
Internal event-management task, project, calendar, and proposal/quotation tracking tool for EGEN's Johor Bahru (JB) and Kuala Lumpur (KL) teams.

## Production endpoints
- Frontend: Cloudflare Pages (`egenmaster.pages.dev`)
- Worker API: `egen-master-deck-api.danwei.workers.dev`
- Data store: Cloudflare Workers KV

## Main files
- `index.html`: live single-file frontend (HTML/CSS/JS, no build step)
- `worker.js`: Worker routes for KV storage and optional AI brief generation
- `wrangler.toml`: Worker config and KV binding

## Calendar behavior
Calendar intentionally shows only:
1. Project Event Date
2. Proposal / Quotation Due Date

Sub-task due dates do NOT appear in Calendar.

Calendar scope:
- Danwei (JB or KL profile): JB + KL team calendar
- Chen: KL team calendar only
- Everyone else: personal calendar only

Calendar items are draggable. Dropping a project/brief onto another date updates the underlying project event date or proposal/quotation due date and saves it.

A timezone bug that shifted pure dates one day earlier was previously fixed by avoiding UTC conversion when expanding calendar dates.

## New Brief / Proposal & Quotation flow
- User pastes a raw client brief into New Brief.
- Frontend calls Worker endpoint `/api/generate-brief` when AI is available; otherwise uses offline parser fallback.
- User assigns the generated brief to a team member and selects due date.
- Assigned records are stored in the `briefs` collection.
- New Brief titles are standardized to:
  `Client Name - Event Type - Location`

## Storage
Frontend uses two broad KV values:
- `brief-bar-data`: `{ briefs, briefCounter }`
- `brief-bar-tasks-data`: `{ projects, projectCounter, taskCounter, statuses, schedules, scheduleCounter }`

This means many edits perform a read-modify-write of a whole JSON blob.

### Important concurrency risk
The current KV design is vulnerable to last-write-wins / lost updates when multiple users edit close together. Example: one user checks a task while another edits a project date from an older in-memory copy; the later full-blob write may overwrite the other change.

This is a key area to audit. A likely production-grade migration is to Cloudflare D1 (row-level records) and/or Durable Objects for coordinated writes. Do not migrate without a backward-compatible data migration plan and rollback strategy.

## Known technical-debt signals to audit
- `index.html` grew through many incremental patches.
- Look for duplicate functions, repeated state loads, dead UI/code, outdated comments, unreachable sections, and inconsistent terminology.
- `loadTasksFromStorage()` has historically accumulated repeated `schedules = ...` / `scheduleCounter = ...` lines; verify current file and remove duplicates safely.
- Some hidden legacy Team/brief UI code may still exist even if not rendered.
- Several date helpers use `new Date().toISOString().slice(0,10)`; audit for Malaysia timezone correctness wherever date-only semantics are intended.
- Access control is UI-based only; users may be able to switch identity or call Worker APIs directly.
- Worker storage API should be reviewed for authentication, authorization, input validation, CORS, abuse protection, and destructive operations.
